# Project_template

## Задание 1. Анализ и планирование
### 1. Описание функциональности монолитного приложения
>**Управление устройствами**:
- При установке специалистом сенсора пользователю, последующее создание информации об этом в системе;
- Пользователи могут удалить информацию о сенсоре из системы при необходимости.

>**Сбор телеметрии:**
- Пользователи могут получать данные о показаниях счетчиков в своих домах;
- Система поддерживает получение данных как и по идентификатору сенсора, так и по его локации.

>**Управление отоплением:**
- Пользователи могут включать и выключать отопление в своих домах;
- Система поддерживает динамически заданное пользователем значение для сенсора.

### 2. Анализ архитектуры монолитного приложения
- Используемый ЯП: `Go v1.22`
- СУБД: `PostgreSQL v16`

Используется классический веб-сервер с архитектурным стилем `REST API` и эндпоинтами по пути - 
`/api/v1/sensors/`. Эндпоинты же, в свою очередь, вызывают необходимые функции DB адаптера и 
возвращают ответ в виде `JSON`. Момент, который стоит упоминания - `GET` эндпоинты помимо простого
получения данных из БД, также, если сенсор имеет тип `temperature` через сервисный слой делают
`HTTP` запрос до другого сервиса и обновляют значения температуры, статуса и времени последнего
обновления данных с "последних актуальных данных".

### 3. Определение доменов и границы контекстов
>**Управление устройствами**:
- Ответственность - учет инвентаря оборудования, регистрация после физической установки, деактивация
- Единый язык и сущности - `Устройство`, `Серийный номер`, `Статус`, `Тип`
>**Сбор телеметрии**:
- Ответственность - получение, обработка и сохранение потока показаний от различных датчиков,
агрегация и возврат последних актуальных данных/исторических данных по запросу
- Единый язык и сущности - `Метрика`, `Источник метрики (серийный номер устройства)`, `Время`,
`Локация`
>**Управление отоплением**:
- Ответственность - контроль температуры датчиков, соблюдение правил аварийной безопасности
- Единый язык и сущности - `Температура`, `Единица измерения`, `Аварийный режим`

### 4. Проблемы монолитного решения
- В `GET` запросах мутировать исходные данные исходя из ответа от другого сервиса - неэффективно и
не надежно, особенно это плохо выглядит по пути множественного получения датчиков
`GET /api/v1/sensors`, т.к пропорциально количеству сенсоров, в цикле вызывается столько же `HTTP`
запросов к другому сервису, что потенциально может быть очень дорогой операцией, даже если это было
бы асинхронно;
- Нет никакой системы авторизации, любой пользователь может получить данные с сенсора любого другого
пользователя, или что еще хуже - поменять любую информацию о чужом сенсоре или вовсе удалить его;
- Удаление записей о счетчиках в БД через оператор `DELETE` считается плохой практикой и лучше было
бы тогда использовать специальный булевый флаг под это или определенный статус обозначающий удаление;
- Если пользователи массово начнут делать запросы на получение телеметрии сенсоров и поды с
приложением станут не справляться с резко возросшей нагрузкой - нам придется масштабировать все
приложение целиком, даже если других запросов, например, на добавление устройства, будет минимальное
количество.

## Задание 5. Работа с docker и docker-compose
Перейдите в apps.

Там находится приложение-монолит для работы с датчиками температуры. В README.md описано как запустить решение.

Вам нужно:

1) сделать простое приложение temperature-api на любом удобном для вас языке программирования, которое при запросе /temperature?location= будет отдавать рандомное значение температуры.

Locations - название комнаты, sensorId - идентификатор названия комнаты

```
	// If no location is provided, use a default based on sensor ID
	if location == "" {
		switch sensorID {
		case "1":
			location = "Living Room"
		case "2":
			location = "Bedroom"
		case "3":
			location = "Kitchen"
		default:
			location = "Unknown"
		}
	}

	// If no sensor ID is provided, generate one based on location
	if sensorID == "" {
		switch location {
		case "Living Room":
			sensorID = "1"
		case "Bedroom":
			sensorID = "2"
		case "Kitchen":
			sensorID = "3"
		default:
			sensorID = "0"
		}
	}
```

2) Приложение следует упаковать в Docker и добавить в docker-compose. Порт по умолчанию должен быть 8081

3) Кроме того для smart_home приложения требуется база данных - добавьте в docker-compose файл настройки для запуска postgres с указанием скрипта инициализации ./smart_home/init.sql

Для проверки можно использовать Postman коллекцию smarthome-api.postman_collection.json и вызвать:

- Create Sensor
- Get All Sensors

Должно при каждом вызове отображаться разное значение температуры

Ревьюер будет проверять точно так же.
